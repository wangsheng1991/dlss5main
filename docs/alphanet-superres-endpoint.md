# AlphaNet second endpoint (vendor brief)

Received 2026-09-17 from the AlphaNet operators and copied here verbatim, so the contract lives with
the code instead of in a chat. Read it before touching super-resolution wiring.

**What this actually is:** the same `flux-klein` image-edit API, with the same base URL, model name,
endpoint paths and request/response shapes, reached with a *second project key*. The key decides which
compute cluster the traffic lands on (the old key keeps the original production instance; the new key
uses the expansion cluster). It is **not** a pixel-exact 2×/4× upscaler: the output size follows the
`width`/`height` you ask for (multiples of 16), and the content is regenerated by the same model, so
nothing here justifies advertising "true super resolution".

- Client: `alphaNetSuperRes` in `api/_lib/alphanet.ts`, key from `ALPHANET_SUPERRES_API_KEY`
  (reported as `superResKey` by `GET /api/health`; it does not affect the health status).
- Status: key not delivered yet, so the instance is present but unused. Coding is possible without it;
  only the live run is blocked. `shared_env/alphanet/acceptance-superres.mjs` runs the §2 checklist the
  moment the key exists.
- Traps that already cost us a change: PNG results are not a bug (do not name downloads after
  `output_format`), and `image_ids` is capped at 4.

> 整份复制过去即可开工。

## 1. 能确定的部分（现在就能照着实现）

**这是一个和你们已经在用的 AlphaNet 图片编辑 API 完全同构的第二个端点。**
Base URL、模型名、端点路径、请求/响应结构都相同；**唯一区别是换一个项目 API Key**。

- Base URL：`https://dashboard.alphanetplus.com`（不要用 `api.alphanetplus.com`）
- 鉴权：`Authorization: Bearer <项目 API Key>`（**只放后端环境变量**，例如 `ALPHANET_SUPERRES_API_KEY`）
- 模型名：`flux-klein`
- 客户端的项目 Key **决定了流量去哪条算力**：老 Key 仍走原来那台生产实例（一行不用改），
  新 Key 走扩容集群。调用方不需要改任何请求体字段，**换 Key 就切线路**。

### 1.1 四个调用（原生 fetch 版本，不依赖任何 SDK）

```js
const BASE = 'https://dashboard.alphanetplus.com';
const KEY  = process.env.ALPHANET_SUPERRES_API_KEY;   // 新项目 Key，仅后端
const UA   = 'your-saas/1.0';   // 服务端若用 Python urllib，必须自定义 UA（见 §4.2）
const H    = { Authorization: `Bearer ${KEY}`, 'Content-Type': 'application/json', 'User-Agent': UA };

// ① 申请输入图上传票据（后端）
const ticket = await (await fetch(`${BASE}/v1/flux/uploads`, {
  method: 'POST', headers: H,
  body: JSON.stringify({ model: 'flux-klein', file_name: 'input.png',
                         content_type: 'image/png', size: fileSizeInBytes }),
})).json();
// → { file_id, upload_url, method:"PUT", headers:{"Content-Type":"image/png"},
//     expires_in:900, max_size_bytes:20971520 }

// ② 浏览器直传 R2（前端；不带任何 Key）
// await fetch(ticket.upload_url, { method:'PUT', headers: ticket.headers, body: file });

// ③ 提交编辑任务（后端）
const opKey = 'operation-uuid-…';                     // 每个逻辑编辑操作唯一，重试必须复用
const sub = await (await fetch(`${BASE}/v1/tasks/alphanet-flux`, {
  method: 'POST', headers: { ...H, 'Idempotency-Key': opKey },
  body: JSON.stringify({ model: 'flux-klein', prompt: '把参考图的灰面板改成亮红，其余不动',
                         image_ids: [ticket.file_id], width: 1024, height: 1024, seed: 42 }),
})).json();
// → { task_id: "task_FM30n…", status:"queued", model:"flux-klein", id: <同上>, created_at: 1789638186 }
//   注意：任务号是网关自己发的 "task_" + 22 位，不是 32 位 hex。

// ④ 轮询（推荐 include_result=true）；GET /v1/tasks/{task_id}/result 可单独刷新结果链接
const st = await (await fetch(`${BASE}/v1/tasks/${sub.task_id}?include_result=true`,
                              { headers: H })).json();
// st.status ∈ queued | IN_PROGRESS | SUCCESS | FAILURE（只有 SUCCESS 才带 st.result）
```

```json
              "url":"https://<account>.r2.cloudflarestorage.com/...&X-Amz-Signature=…"}],

   "request_id":"ac54731491fd4379ab2f7ae92909b89b","gpu_index":2,"worker":"home-linux"}}
```

- `result.images[].url` 是 **900 秒有效的签名链接**，过期用 `GET /v1/tasks/{task_id}/result` 换新的；
  不要把签名 URL 当永久地址，也不要记进日志。
- `worker` / `gpu_index` / `request_id` 是内部调度信息，可能缺字段，**不要依赖**。
- 从本机实测：提交到完成约 7 秒（服务端报 `timings.total` 2.4 秒，排队/取图/上传另计）；仍按异步任务设计。

### 1.3 参数约束与错误表（全部实测）

约束：`image_ids` **1–4 个**已上传且属于本项目、未过期的 `file_id`；`width`/`height` 必须是 **16 的倍数**；
`size` 与实际字节一致且 ≤ 20 MiB；支持 `image/png`、`image/jpeg`、`image/webp`。

| HTTP | 响应体（节选） | 触发 |
|---|---|---|
| 400 | `{"error":"invalid_upload"}` | 类型不支持（如 gif）、`size` > 20 MiB 或与实传不符 |
| 400 | `{"code":"plugin_request_invalid","message":"… image_ids must contain 1 to 4 …"}` | `image_ids` 空 / >4 |
| 400 | `{"code":"plugin_request_invalid","message":"… prompt is required …"}` | `prompt` 空 |
| 401 | `{"error":{"message":"Invalid token …","type":"new_api_error"}}` | Key 缺失/伪造/过期/额度用尽 |
| 404 | `{"code":"fail_to_fetch_task","message":"{\"error\": \"Input file not found or expired\"}"}` | `file_id` 不存在、过期或**不属于本项目** |
| 404 | `{"error":{"message":"Task not found","type":"invalid_request_error"}}` | `task_id` 不存在或不属于本项目 |
| 409 | `{"error":"idempotency_key_conflict"}` | 同一个 `Idempotency-Key` + 不同请求体 |
| 422 | `{"code":"fail_to_fetch_task","message":"{\"error\": \"width 必须是 16 的倍数\"}"}` | 尺寸非 16 倍数 |
| 503 | `{"error":{"code":"model_not_found", …}}` | 模型名不是 `flux-klein` |

### 1.4 幂等与计费（照做）

- 同一 `(Key, Idempotency-Key, 请求体字节)` → 返回**同一个 `task_id`**，不重复计费。
- **不传 `Idempotency-Key` 也会创建新任务**，只是会重复计费 → 一定要传。
- 幂等比对的是**原始请求字节**：同一条逻辑操作始终用同一段序列化代码，不要跨语言重序列化。
- 超时/网络错误时用**原 Key + 原 Idempotency-Key + 原请求体**重试；不要换 Key 重提。
- 失败任务按已验证流程退款，但以你们自己的任务与账单记录核对。

## 2. 验收（拿到真 Key 之后）

1. 成功路径：真实图片跑通，下载结果并核对 `sha256` 与 `file_size` 一致；
2. 幂等：同键同体重提 → 同一个 `task_id`；同键异体 → 409；
3. 隔离：用新 Key 查一个老项目的 `task_id` → 404 `Task not found`（已由我方实测确认成立）；
4. 失败路径：坏尺寸/空 prompt → 4xx，且不产生挂住的收费任务；
5. 回归：老项目那条链路（老 Key）行为不变。
   我方还能配合：真 Key 到手后，可由我方跑一次 8 项端到端脚本出具报告（上传 → 直传 → 提交 →
   幂等重放/冲突 → 轮询 → 取结果 → sha256）。

## 4. 注意事项（都是踩过的）

1. **目前产物只有 PNG**：即使请求 `output_format:"webp"` 也回 `image/png`，请按返回的
   `content_type` 处理，不要按请求值写死扩展名。
2. **Cloudflare 挡默认 User-Agent**：实测 `User-Agent: Python-urllib/3.6` → **403**；
   `curl/8.0` 或自定义 UA → 200。Node/浏览器不受影响。
3. **任务号是 `task_` + 22 位**（网关自己发的），不是 32 位 hex；校验脚本别按 hex 写。
4. **结果链接 900 秒过期**；`uuid`/`sha256`/`file_size` 可用于校验与去重。
5. **`GET /v1/models` 不校验 Key**（不带 Authorization 也返回 200，只列模型名）——
   不能拿它验证 Key 有效性；要自检 Key，用 `GET /v1/tasks/<自己项目的 task_id>`（无效 Key → 401）。
6. 新项目与老项目**互相隔离**：任务、上传的文件、配额、令牌都是分开的，可以放心把
   `task_id`、`file_id` 暴露给你们自己的前端。
7. 不要让单次 HTTP 请求等待整段推理（Vercel 上尤其），沿用"异步提交 + 轮询"的模式。
