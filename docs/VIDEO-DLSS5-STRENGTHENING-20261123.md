# 视频与 DLSS5 线：先补哪一格（2026-11-23）

按「卡成交」排序，不按「听起来厉害」排序。排序依据取 `docs/ORDERS-2-3-20261123/ORDERS-2-3.md` 的缺口表与自己实测的两条：身份保持是概率的、第三张场景参考成立。

## 一、视频线：现在缺的不是模型，是「收货口」

现状（仓库核实）：`/video-upscaler`、`/frame-interpolation` 页面在线，但**没有真链路**——上传、报价、处理、下载、失败退款，五步一个都没有。已有的只是交付物工具（帧包、分镜清单），它们不能替代超分成片。

所以第一期只做一件事：**先体检，再报价，不承诺处理**。

| 步骤 | 交付物 | 最小可用版本 |
| --- | --- | --- |
| 1. 体检 | 客户端读出时长、分辨率、帧率、码率、总帧数 | 浏览器 `<video>` 元数据 + 用户填的容器/编码；一屏结论「能不能进队列」 |
| 2. 报价 | 帧数 × 单价 + 目标分辨率，给区间不给精确值 | 纯函数 + 单测；单价从现有定价页来，不新造 |
| 3. 排队 | 明确写「当前为意向登记，不收款」 | 现有 `/download` 那套 Cloudflare Worker 表单可直接复用 |
| 4. 处理 | 接通后再做 | 需要上游给出固定的超分/插帧请求契约（`api/_lib/alphanet.ts` 已留 `alphaNetSuperRes`，契约未定） |
| 5. 交付与退款 | 失败自动退 | 依赖 4，现在不做 |

判定标准：体检和报价上线后，看**有多少人填了时长/分辨率并点「登记意向」**。这个数比访问量有意义，也是决定要不要投入 4 的唯一依据。

## 二、DLSS5 线：把「能出图」变成「能验收」

已经做掉的两格：第三张场景参考（成立）、生成后并排对脸（已上线）。下一步按性价比：

1. **输入体检**（对应照片）：正脸、平光、脸占画面比例——今天靠教程文字教，改成进门前就提示。实测依据：`you.jpg` 3/13 vs 平光 13/13。
2. **姿势清单从 4 个扩到「姿势 + 机位 + 接触方式」**：机位已上线；接触方式是「手搭肩 / 牵手 / 递物」这类，仍写死在提示词里，扩它比扩姿势便宜。
3. **一次生成、两张候选**：身份是概率的，用户要重跑就得再花一次额度；改成一次出两张、只收一次，成功率明显上去，成本可控（上游 ~12 s/张）。
4. **不要做**：通用搜图 Agent、完整公开 API 平台——没有证据能比现在更快出单。

## 三、这两条线共同的闸门

- 没实测过的能力，不许写进页面和文章（`docs/CORE-POSITIONING.md` R5）。
- 每加一个能力，配一条可复现的实测脚本和一份结果记录；没有记录的能力算没做。
- 付款仍是 Waffo 单通道；任何涉及收款的动作都要老板本人走完一次真实付款再谈。
